### 4.37 后端算得对，但有两个「口径」在冒充同一个数（SM4 用例一核对）

触发：`/bca/` 上跑 SM4 / MAP / 1–4 轮（任务名 `probe-r1-4`）得 `ProbWeightBound = [0,0,0,6]`，
与平台自己那份 SM4 基准（4 轮 44.00）差 7 倍，被怀疑「后端不是 bca_light 的代码」。

**① 后端身份：是真代码。** 四条互不依赖的证据 ——
`readlink /proc/377/cwd` = 本项目根（`python3 manage.py runserver 0.0.0.0:8011 --noreload`；
8011 的 owner 是 `wslrelay.exe`，不是 Windows 侧 `python.exe`）；
`/proc/377/environ` 无 BCA / DJANGO 覆盖；`bca/` + `models/` + `cipher/` + `main.py` 是 BCA_Light 本体
（真调 kissat，非 mock）；输出与 `.workbuddy/memory/2026-09-20.md` 首次跑通时逐项一致。

**② `[0,0,0,6]` 可证正确（真加密验过，不是口径辩论）。**
SM4 的 S 盒输入差 `s = ΔX₁⊕ΔX₂⊕ΔX₃`；取 `Δ = (b,b,b,0)` 时 `s₁=s₂=s₃=0` ⇒ 三轮 S 盒恒不活跃
⇒ **概率恒为 1**（实测 20000 次随机明文、0 次不匹配）→ 1/2/3 轮下界**必然**是 0。
再推一轮 `s₄ = b`，要它为 0 只能 `b = 0` ⇒ 4 轮**至少 1 个活跃 S 盒**；
SM4 的 DDT 元素皆偶 ⇒ 最大 DP 4/256 ⇒ 权重最小 6，且后端 P6 SAT 可达 ⇒ **4 轮下界 = 6**。
（复核脚本在 `outputs/BCA后端核对/`：`verify-sm4-diff-path.py` / `audit-sbox-constraints.py` /
`probe-bit-order.py`。）

**③ 前端那个 44 问的是另一个问题 —— 别再当「SM4 差分下界」用。**
`feistelCharacteristicSearch()` 的起点**写死了 16 个「单字单比特」差分**
（`v[w] = 1 << b`，w∈0..3、b∈0..3），再往下做 beam 束搜索（默认 `beamWidth = 8`）。
它拿不到 `(b,b,b,0)` 这类退化差分 ⇒ 给出的是**该起点族的上界**。
对照（`frontend/tests/_probe-sm4-front.mjs`）：1/2/3/4/8 轮 = `0/6/30/44/135`，后端 = `0/0/0/6`。
32 轮的 687.00 同理是**上界**（后端 `KNOWN_ACTIVE_SBOXES[32] = 32` ⇒ 权重约 192 起）。
`verify-core.mjs` 里那句「权威，勿质疑」对**数字**成立（可复现），对**语义标签**不成立。

**④ `bca_light` 唯一的真缺陷：路径打印把比特序反了。**
`details/path/R<n>-P<p>.txt` 按 LSB-first 打印，而模型内部与 espresso 数据都是 MSB-first。
状态字要按**整体 32 位反转**读回（穷举 4 种位序 × 4 种 S 盒变体，只有这一种命中，p ≈ 2^-5.94）。
后果：一条正确特征会被打印成**不可能**的样子 —— `R4-P6` 打印 `in=0x9F out=0x54`（真 `DDT = 0`），
按位序读回是 `0xF9→0x2A`（`DDT = 4` ⇒ 权重 6）✔。**求解 / 权重 / 判定完全不受影响**，只坑人工核对
（本次核对就先被它带偏）。**改不改 `bca/util/path.py` 的打印位序 —— 定夺结果：不改**（它属
「逐字节移植参考实现」的部件，不代改；口径标注与精确下界展示已落地，见 ⑤）。
待办清单原本在 `outputs/BCA后端核对/README.md` §6，现已结清。

### 4.38 「拼图」实测：非平衡 Feistel + 宽查找表 —— 卡在「宽度」和「拼接」，不卡在查找表

用户给的第三个实操样例：**96 位 / 4 轮**，每轮 `96 → L(32) + R(64)`（非等分）；
`LUT` 取 R 的**高 16 位** → **32 位**固定映射；`G` 取 R 的**低 48 位**过 3 个 **16×16 S 盒**；
更新 `新L = G(R_low48) XOR 旧L`、`新R = LUT(R_high16) ‖ R_low48`（移位后拼接）。
留档 `outputs/BCA-拼图能力测试/`（README + 2 个探针 + 运行日志），独立复核 `verify-pintu.mjs`（**46 项**）。

**先说四个验证要点的答案（都实测过）：**

| 要点 | 结论 | 卡在哪 |
|---|---|---|
| ① 非等分（32+64）分割 | ⚠️ 单字内 A/B 宽度可不同；**32+64 不行** | `INPUT.bits` / `SPLIT.splitBits` 上限都是 **32** ⇒ **没有节点能承载 64bit 的 R** |
| ② 16bit 入 / 32bit 出查找表 | ✅ **已可正确使用**（本轮修复后） | 修前会算错（见下）；宽输出线性侧**显式标注不支持** |
| ③ 高 16 / 低 48 提取 + 重新拼接 | ❌ 提取仅限 ≤32bit 字；**没有「移位后拼接」节点** | `MERGE` 只有 `xor/add/and`（同位置合并）；`LINEAR` 有 `rotl/rotr`，但**没有「左移补零」** |
| ④ 左右不等宽 + 功能不对称的连线 | ⚠️ 分割与连线能表达宽度差 | 迭代内核 `feistelGraphProfile` 只取**一个** `branchBits`（两侧同宽 ⇒ 只支持对称 Feistel）；端口**不标位宽** |

⇒ **「拼图」整体搭不出来，卡在 ① 与 ③，不是卡在 ②。** 但 ② 这个「能搭出来却算错」的坑是**真缺陷**，已修：

**修掉的四处（前三处都是「同一语义两处实现 / 边界未处理」的老毛病）：**

- **D1 `SBox.outSize` 的 JS 回绕**：`1 << outBits` 在 `outBits ≥ 31` 时坍缩 —— `1<<32 === 1`、
  `1<<31` 变负数。于是 32bit 输出的查找表 `outSize = 1`，下游 `for (b = 1; b < outSize; b++)`
  一次都不跑 ⇒ DDT/LAT 全零、`bestTransition` 报 **`prob = 0`**。修：`outBits >= 31 ? 2 ** outBits : (1 << outBits)`，
  并引入 `SBOX_TABLE_CAP = 1<<24` + `fullTableFeasible()` 作为「能不能建全表」的唯一判据。
- **D2 非等宽 S 盒的「平铺 OR」**：`splitSBoxInputs` 的 `'parallel'` 分支按**输入位宽**（16）为步长平铺，
  于是 16→32 的 32bit 输出会与相邻块**重叠 OR**。实测 `0x00010001` 查表结果错。修：`inBits !== outBits`
  时**整字一次查表**（不再平铺）。**这一条是「能搭出来、也能加密，但掩码级算错」的典型。**
- **D3 掩码级与值级自相矛盾**：D2 的连带后果（D1 放大）—— 同一次查表，值级确定、掩码级 `prob=0`。
  修 D2 后掩码级 ≡ 独立穷举。顺带在 `TraceStep` 上补**结构化布尔** `unsupported`（此前只有中文 note）——
  判语义不许正则匹配文案。
- **D4 大盒把 `analyze()` 打崩**（附带）：16×16 盒的 DDT 全表 `65536×65536 ≈ 4.3G cell`（Uint16 也要 8GB），
  指标日志 / 分支搜索无条件建表 ⇒ 抛错。修：`getDDT()/getLAT()` 超限**显式抛错**（可预期的拒绝，
  不是静默假表）；差分改走**按需单行** `ddtRowOnDemand`（O(inSize)，**精确**）；线性侧返回
  **显式「不支持」占位** `unsupportedWideOutput`，**绝不返回 0 冒充**零相关。

**为什么这次「修了边界却不改任何基准值」**：修的全是 8bit 方盒之外的路径。`verify-pintu.mjs`【0】
专门锁 `8bit outSize = 256`，并**独立按公式重算** LUT、**独立穷举**差分行与引擎对拍（10bit 盒
6 × 1024 = 6144 组零不符）—— 所以 SM4 / 类 AES / 双鱼的权威值**一个字没动**。

**独立复核为什么可信**：① 差分分布用与 `analysis.js` **无关的第二份**穷举代码算；② LUT 不读平台存下来的表，
按公式 `imul(x,0x9E3779B1) ^ (x<<21)` 重算；③ 专挑「平台自相矛盾」的判据（掩码 `prob=0` vs 值级确定）；
④ 源码守卫钉死「不许回退」的写法（`outSize` 不许写回 `1 << outBits`、`ddtRowOnDemand` /
`unsupportedWideOutput` 必须存在、非等宽盒必须整字一次查表）。⚠️ 本例**没有浏览器留档、没有 session.json**
（整图搭不出来）—— 独立复核是**纯 Node 的独立穷举对拍**，故意不依赖 `design-*.cjs` 产物。

**顺带记两条平台事实**：`SBOX` 节点**没有「输出位宽」入口**（输出宽由所引用的 S 盒决定）；
`graphBlockSize` 的 `blocks` 派生（32×3 = 96）**只是界面显示**，引擎只看 `graphBlockBits()`（≤32）。
### 4.39 「跑得快，结果对不对」复核：默认参数对，调大「分支上限」会错（10-16 实测）

用户问「算法跑那么快，结果是否正确」。复核手法：**独立重算 + 真实加密抽样 + 与 BCA 全空间精确解对照**
（永久套件 `frontend/tests/verify-accuracy.mjs`，54 项；`npm run test:accuracy`）。

**结论分三层，别混着说**：

1. **快是因为「按公式算」，不是「数明文对」**：引擎沿一条选定差分路径把各活跃 S 盒的 DDT 表项概率
   **相乘**（Markov 假设）。32 轮 `−log₂p = 647` 对应的暴力计数需 `2^647` 对样本 —— 不可能；引擎 **440ms**
   给出结果。耗时对轮数**近似线性**（R8 96ms → R16 210ms → R32 440ms，无指数爆炸），起点只有 ~48 条
   （16 条单字单比特 + 32 条「三轮免费」族）。
2. **默认参数下报出的每条特征都真实可达**：另写一份 **256×256 暴力 DDT** + 另写 L 变换，逐轮重算 ——
   权重与 Δout 与平台**逐位相等**（R = 4/5/8/16/32）；再用**真实 SM4 加密**（`sm4ref.js`）抽样：3 轮确定性
   `3000/3000`、4 轮实测 `2^-5.972`（理论 `2^-6`）、5 轮 BCA 路径实测 `2^-12.086`（理论 `2^-12`）。
   ⇒ **R1~R4 与 BCA 全空间精确解相等**（`0/0/0/6`），这几档就是精确最优。
3. **5 轮起是权重上界**，不是全局最优。差距在**默认起点集合覆盖不足**，不在搜索算法 ——
   束宽 8/24/64、分支上限 1~64 全试过，R5 恒 `30.00`；把 BCA 那条 2 盒路径入口
   `Δin = (0x4d31317c, 1, 1, 1)` 喂进**同一个引擎** → 立刻 `12.00`（逐轮活跃 `R1:a1 R2:a0 R3:a0 R4:a0 R5:a1`）。

**⚠️ 复核揪出并修掉的真缺陷：`enumTauBranches` 丢活跃字节（「分支上限」越大反而越错）**

旧代码逐字节做候选笛卡尔积时写 `combos = nxt; if (combos.length > 256) break` —— 候选数乘积一旦超过
256 就 break，**把后面还没展开的活跃字节整块丢掉**，于是 `τout` 里那些字节恒为 0；而对非零输入差分
`DDT[Δ≠0][0] ≡ 0`（S 盒是双射：`S(x)⊕S(x⊕Δ)=0 ⇔ Δ=0`）⇒ 该分支**真实概率为 0**。
症状：**调大「分支上限」反而报出物理上不可达、且更小（看着更优）的权重** —— 像"搜得更深找到了更好的特征"。
阈值：4 个活跃字节时 `7³ = 343 > 256` ⇒ **`branchLimit ≥ 7` 触发**，而界面范围正是 **0~64**
（默认 `0` = 自动 → 实际用 4，**所以权威基准值一直是对的，这也是它长期没被发现的原因**）。

| branchLimit | 修复前平台 w | 独立重算 w | 修复后 |
|---|---|---|---|
| 1 ~ 6 | 30.00 | 30.00 | 30.00 |
| 7 / 8 / 16 | **24.00** | **∞（概率 0）** | 30.00 |
| 32 / 64 | **18.00** | **∞（概率 0）** | 30.00 |

修法：① **不再 break**，改为「逐字节只保留概率最高的 `limit` 条前缀」—— 该截断对「全体候选里概率最高的
`limit` 条完整组合」**精确**（同后缀 ⇒ 前缀不劣则组合不劣），规模恒为 `O(limit)`；② 加**防御断言**
「活跃字节输出为 0 的组合直接丢弃」（宁可不输出，也不报假特征）。修后 `branchLimit` 1~64 全档恒 `30.00`，
且 32 轮由 `647.00` **真改善为 `646.00`**（放大候选确实能搜到更优的真实特征）。

**连带的断言翻转（`verify-core.mjs`）**：曾有一条断言锁「`branchLimit=8` 时两模型开始分叉
（PWM 505.00 / PMM 511.00）」—— `505/511` 远低于真实可达的 `646.00`，是丢字节造成的假"更优"。
修后两模型在同一条真实特征上重合，断言改为「bl=8 两模型均 `646.00`」+「bl=64 **不得 < 646.00**」
（单边：12s 预算会截断这一档，故不锁精确值）。

**顺带修正口径方向错误**：页面原写「`−log₂p` 是**概率的**上界」—— **方向反了**。正确说法：
**`−log₂p` 是权重上界（等价地，概率是下界）**；真实最优特征的权重只可能更小、概率只可能更大
⇒ 上报数字会把攻击难度说得**比实际高 = 偏乐观**，**不能当安全性保证**。已改 `ResultsView.vue` /
`AnalysisView.vue` / `HomeView.vue` / `core/bca-reference.js` 头部，并加守卫（页面不得出现
「概率的…上界」，且必须把「`−log₂p` 只可能更小 ⇒ 概率 ≥ 2^w」钉在数字旁）。

**证据链**：`outputs/BCA-速度与正确性复核/`（README + 2 份探针 + 3 份运行日志 + **修复前原始输出对照**）。
演示话术与「能说 / 不能说」清单同步见该 README §五。

### 4.32 8011 的"静默遮蔽"：WSL 的转发在 Windows `netstat` 里叫 `wslrelay.exe`

「后端跑不了」**最可能的病因不是崩溃，是端口遮蔽**，而且它 100% 静默。

机制：`scripts/wsl-server.sh` 在 WSL 内绑 `0.0.0.0:8011`，靠 WSL2 的 localhost 转发给 Windows 浏览器。
这时 Windows 侧若还留着一个 `manage.py runserver 127.0.0.1:8011`：

- **Windows 赢下这个地址**（更具体的绑定优先），浏览器打到的是 Windows 那个 Django；
- Windows 的 Django 只能回 `status().available = false / reason = needs_linux`；
- 于是 `/bca/` 永远说"要 Linux"，**毫不知情的用户以为 WSL 那份坏了**，其实它好好的。

**判定谁占着 8011 时，必须看进程名，不能只看有没有 LISTENING**：

| `netstat -ano | findstr ":8011 "` 里的 owner | 含义 | 该怎么办 |
|---|---|---|
| `wslrelay.exe` / `wslhost.exe` | **WSL 自己的转发**，后端已在正常运行 | 直接开浏览器；不要再起第二个（WSL 内会 bind 失败） |
| `python.exe` 等其它 | **真的 Windows 遮蔽** | 杀掉该 PID 再起 WSL |

⚠️ 上一轮我记过一条**已被实测推翻**的结论：「WSL 里的服务在 Windows `netstat` 里看不到 LISTENING」。
**错的** —— 它看得见，只是进程名是 `wslrelay.exe`。据此写的守卫会把 WSL 自己误判成入侵者、
叫人去杀一个不存在的 Windows 进程。`start-platform-wsl.bat` 现已改为按进程身份分流：
`wslrelay/wslhost` → 打印 INFO + `exit /b 0`（不启动第二个）；其它 → 打印 ERROR + `exit /b 1`。
守卫里用了 `!OWNERPID!`，所以那个文件是 `setlocal enabledelayedexpansion`，**别改回普通 `setlocal`**。

四个分支都实测过：空闲→放行 / `wslrelay`→INFO(rc=0) / Windows `python.exe`→ERROR(rc=1) / 负对照
（`python.exe` 不匹配 relay 关键字）。验证手法可复用：把守卫原样抽出、只改 `PORT=8012` 落到临时
`.cmd` 里跑，这样不动正在服务的 8011。另注：`pause` 会打印**本地化的**「请按任意键继续」，
所以那两段的输出不是纯 ASCII —— 抓取时要按 GBK 兜底解码。

### 4.33 「能画 ≠ 能算」：图必须真的被当回事（四个已修缺陷）

结构编辑器**能画**（拖组件、连线、改属性）不等于引擎**会按它算**。曾经有四个断点，让用户手搭的图
在界面上看着成立、算出来却是别的东西 —— 症状全是「不报错，只是数值与画布矛盾」，最难查。
现在四处都堵上了，**改动这四块前先读本节**：

| # | 旧症状 | 现在 |
|---|---|---|
| ① | `meta.structure` **界面上根本没有入口**，只由 `graph.js` 模板 builder 写入 → 手搭的 Feistel 永远带 `spn` 标记，中文解析把它定性成「SPN：每轮对整个状态做 S 盒代换」 | 编辑器元信息面板有**「结构类型」下拉**（SPN / Feistel / 广义 Feistel），选什么就按什么算 |
| ② | 图一旦标 `feistel`，`platform.js` 就路由到 `sm4RoundProfile()` —— 那个函数**不收 graph 参数**（SM4 专用）。铁证：2 节点的空图标 feistel 与真 SM4 模板 8 轮**逐项同值** | 新增 `feistelGraphProfile(graph, opts)`：真沿这张图做「分割 → 分支 → 交叉 → 交换」迭代 |
| ③ | 掩码传播是 `inMask \|= state.get(e.from)`，**端口不参与** → SPLIT 写的 `\|a`/`\|b` 只写不读，「右半进 F、再与左半异或」退化成「整字或在一起」 | 新增 `outMaskAt(state, nodeId, portId)`：先取 `state['node\|port']`，没有才回落到 `state[node]` |
| ④ | 图上选的 S 盒与位宽到不了引擎：`params.js` 写死 `sboxRef: 'sm4'` / `blockBits: 32`；`meta.blockSize` 又能随手改成 64 与引擎自相矛盾 | `buildSearchOptions` 从图派生 `blockBits` / `engine` / `sboxRef`（取图里第一个 SBOX 节点的盒子）；`blockSize` 变成**只读派生**（= INPUT 位宽 × 分块数） |

配套的几处「同一条路走两遍会不一致」的坑：

- **`engine` 标记只许落在内置 SM4 模板上**。`graph.js` 里只有 `sm4` 与 `sm4_keyext` 带 `engine: 'sm4'`；
  其余一律走通用图引擎。`platform.js` 按 `opts.engine === 'sm4'` 分流 —— **别再写成
  「线性模式或 feistel 就送 SM4 引擎」**（那正是缺陷②的老写法）。
- **单次运行与全轮扫描必须共用同一条分流**（`runProfile()`）。否则收敛曲线和单次结果对不上，
  而且错得毫无提示。
- **`SPLIT` 切分要挡住 `>>> 32`**：`const a = (inMask & maskOf(sb)) >>> 0; const b = sb >= 32 ? 0 : ...`
  —— JS 的移位量是按 32 取模的，不挡的话 `sb >= 32` 会变回整字，分支又白设了。
- **元信息面板与属性面板是同一个 card 的二选一**（`v-if="!selected"`）。所以点了节点就回不到
  「结构类型」，除非有取消选中的路径 —— 因此画布空白处绑了 `@click.self="deselect"`。

  **别把这个 deselect 删掉**，否则缺陷①的界面入口等于不可达。
- 抽样命中率验证（`runEmpirical`）在 `engine !== 'sm4'` 时**诚实拒绝**而不是硬算 ——

### 4.34 「真拖真点」才暴露的三个缺陷（引擎两个 + 界面一个）

§4.33 那四个缺陷是**读源码**找出来的。在真实浏览器里从空白画布拖出「双鱼」Feistel
（`design-shuangyu.cjs`）并跑通之后，又在**拖、点、改属性**的过程中抓出三个新缺陷。
共同点：**全都不报错，数字看起来还挺合理** —— 这类 bug 只能靠「外部裁判 + 源码层守卫」夹住。

| # | 旧症状 | 现在 |
|---|---|---|
| ① | 合并写死成**按位或**（`inMask \|= outMaskAt(...)`）。差分域里 `A = L ⊕ F(R)` 与 `A = L \| F(R)` 从**第 3 轮**起就分道扬镳 —— 或运算把「被异或抵消掉的差位」继续留在状态里，后续轮次凭空多出活跃 S 盒。实测双鱼 8 轮被抬成 **84.00 bit / 活跃 14**（真值 66.00 / 11） | `MERGE` 按**节点自己声明的 `props.op`** 合并（默认 `xor`）；`add` / `and` 在差分域没有精确映射 → 保守按并集（数值**必须变**，这正好当守卫用）；前向加密路径同步改，两条路语义一致 |
| ② | 逐轮表的列名是「**输出状态**」，但两条路径语义相反：SPN 塞轮末（`st.diffAfter`）、Feistel 塞轮**首**（`state: [L, R]`）→ 同一列两种含义，最后一行与总览的输出差分对不上 | Feistel 也塞轮末（`state: [Rin, A]`，即交换之后）；轮首状态另存 `stateIn`。不变式：`perRound.at(-1).state === best.outputState` |
| ③ | 属性面板的输入框用原生 `@change` —— 而 **`change` 在失焦时才发**，失焦又晚于下一个节点的 `mousedown`（选中已切走）→「改完 A 的属性、直接点 B」把 A 的值写进了 B 的 `props`。实测：改「输入明文」的分块数 → 落到「分支/分块」上，INPUT 一点没变 | 字段描述符钉住归属节点（`nodeId: node.id`），`setProp(key, value, nodeId = null)` 按 id 定位、**不回退**成「当前选中」；数值 / 文本字段改 `@input`（`<select>` 不在此列 —— 选中即触发 `change`，没有失焦时延） |

几条必须一起记住的：

- ①② 都是「**同一件事在两处实现，走着走着就不一致**」。所以改 `propagateGraphOnce` 时必须同时看
  `forwardEncrypt` 的 `MERGE` 分支；改 `state` 语义时必须同时看 `ResultsView.vue` 的 `hasState`
  （列名就是契约，它和引擎是绑定的）。
- ③ 的守卫只能放在**源码层正则**（`verify-pages.mjs`）—— 「把值写错对象」不改变任何数值，
  数值层测不出来，只能钉写法。
- **引擎自证不算数**：这三个都是 `verify-shuangyu.mjs`（24 项）抓出来的。它不复用平台引擎，
  自己从 GF(2⁸) 重建 AES S 盒、穷举 256×256 DDT/LAT、按导出的图**另写一份传播实现**，
  再把平台逐轮日志里声称的 `A` 拿来判「究竟按 XOR 还是按 OR 算的」。

守卫在哪儿：`verify-pages.mjs` 尾部 ③+ / ⑤ 段（源码层正则）、`verify-integration.mjs` 第【7】节
（数值层，含「末行 state = 输出差分」不变式）、`accept-four-defects.cjs`、`verify-shuangyu.mjs`。

### 4.35 「方阵」SPN 实测：语义里没有的东西，界面也变不出来

用户给的第二个实操样例：AES 风格 **128 位 / 4×4 字节矩阵 / 6 轮**，
`SubBytes → ShiftRows → MixColumns → AddConstant`，末轮省略 `MixColumns`。
留档在 `outputs/方阵SPN设计记录/`，搭建脚本 `design-fangzhen.cjs`，独立复核 `verify-fangzhen.mjs`（50 项）。

**先记住三条平台语义（都实测过，不是猜的）：**

| 想做的事 | 平台实况 | 证据 |
|---|---|---|
| 128 位分组 | `INPUT.bits` 定义里 `max: 32`，往框里填 `128` **当场被夹回 32**（`onPropInput` 按 `field.max` 夹紧）；「分块数」只进 `graphBlockSize()` 供界面显示，引擎只看 `graphBlockBits()`（一律 `min(32, bits)`） | 界面「分组长度 = 128」与日志「词宽 32bit」同屏共存 |
| 行/列操作 | 组件库没有矩阵/行/列节点；`PERM` 只有**一个统一**字节移位量 → 表达不了「第 i 行移 i 个字节」 | `NODE_TYPES.PERM.props` 仅 `shift` / `reverse` |
| 列混淆（GF(2⁸) 矩阵乘 02/03/01/01） | **已有真实现**（`mixColumnsWord`，2026-10-14 修）；但作用范围仍受词宽限制：**32bit = 一列**，不是 4×4 矩阵 | `gf256Mul` / `xtime` 约减 `0x1b` / 分支数 5 |

**`mixColumns` 从前是一个「名不副实 + 两套实现」的组件（缺陷①，**2026-10-14 已修**）：**

- **症状（修前）**：值级 `mixed = bi ^ ((bj<<1)|(bj>>>7)) ^ bj` —— `(b<<1)|(b>>>7)` 是
  **8 位循环左移**，不是 xtime（`0x80` → `0x01`，真值 `0x1b`；256 个输入里 128 个不同）；
  掩码级则把字节掩码**原样 OR 到下一个字节**。同一个 `Δin` 有**三个**答案：
  平台分析 `0x00000101` / 平台自己加密 `0x03000001` / 真 AES `0x03010102`；分支数 3（AES 是 5）。
  掩盖性最强的副作用：掩码级对「四字节全活跃且相等」的状态是**恒等映射**
  （`0xdadadada → 0xdadadada`），于是「末轮省略 MixColumns」在数字上完全不可观测。
- **修法**：只留**一份**实现 `mixColumnsWord()`（真 GF(2⁸)，AES 的 `[02 03 01 01]` 循环矩阵），
  掩码级取它的 **GF(2)-线性延拓**（逐比特基向量 XOR 叠加，`mixColumnsMask()`）——
  两者在 32 个基向量上**必然一致**，「谁才是真列混淆」不再是问题。导出 `gf256Mul` / `gf256Xtime`
  供独立复核对拍。
- **修它的真正成本是连带更新**：类 AES 10 轮 `204.00 / 活跃 34` → **`222.00 / 37`**、
  线性 `180.00` → **`216.00 / 36`**（`222 = 37 × 6.00`、`216 = 36 × 6.00`）；同一轮要改
  `verify-core.mjs`、`TutorialView.vue` 教学示例、`e2e-browser.cjs` 注释。
  `verify-fangzhen.mjs`【10】用**独立光束搜索**（自建 GF(2⁸) + 穷举 DDT）从零复现
  `1→5→9→…→37`，与平台报告值互证 —— 所以这不是「改断言凑绿」。
- 32bit 字 = 一列（标准 AES 列混淆）；不足 4 字节的尾列**零填充成整列再截回**，
  映射仍是 GF(2)-线性的（8bit 字退化为 `xtime`）。

**「末轮跳过某层」的答案：条件逻辑仍然没有，但手工展开现在**完全可观测**：**

- 引擎主循环 `for (r = r0; r <= totalRounds; r++)` 每轮跑**同一张图**，节点语义拿不到轮次；
  所以「按轮次选层」做不到 —— 这是能力边界，不是缺陷。
- 手工把 6 轮展开成一条链（26 节点）+「结束轮 = 1」→ 整条链在**一趟传播**里走完，引擎照图算：
  - 把差异放到第 1 轮：权重 `30.00 → 12.00`、活跃 `5 → 2`、末轮 Δ 也变；
  - 末轮省略 MixColumns：**末轮 Δout 与全层版不同了**（`0xb573e7c7` vs `0xb7023261`）——
    修缺陷①之前这两个值都是 `0xdadadada`（恒等映射导致不可观测）；
  - 而且「展开 6 轮」与「统一轮函数迭代 6 轮」权重与末轮 Δ **完全一致**（两条路径语义统一）。
- 但**末轮的层不改变权重**：代价只统计「各轮进 S 盒的活跃字节数」（两份都是 126.00）。
  教学时要说清楚这一点，否则会以为「少画一层 = 结果应该变小」。

**同批修掉的三处（原缺陷②③④ + 一处隐藏缺陷）：**

- ② 通用图（SPN）路径**从不填 `outputState`** → 结果页「输出差分 / 掩码」恒为 **「(未记录)」**。
  现在主循环补 `ch.inputState` / `ch.outputState`（单字状态塞成单元素数组），
  中文解析与结果页都能读到真值。
- ③ 界面「起始差分 / 掩码」在**通用图路径被忽略**（只有 SM4 专用引擎读它）。
  现在 `analyze()` 与 `feistelGraphProfile()` 都吃 `initDiffs`：四字向量取**第一个非零字**
  （通用图是单字状态），其余非零字记 warn 明说被忽略 —— **不静默丢**。
- ④ 死属性两个：`轮函数容器.展开为独立轮` **已删除**（引擎本来就只有「按轮数迭代」一种语义，
  勾与不勾一样 —— 不留「改了不影响计算」的开关）；`异或轮密钥.独立轮密钥` **接上了语义**
  （`keySchedule(name, round)`：选「是」每轮不同，选「否」各轮复用同一把）。
- ⑤ 顺带发现并修：`forwardEncrypt` 从前**只把图跑一趟**，`rounds` 参数收下就丢 ——
  `avalancheTest` 传 32（SM4）实际只算了 1 轮，「雪崩」与轮数无关。现在按 `rounds` 真迭代。

**通用教训（比缺陷本身更重要）：**

1. **组件的名字不等于它的语义**。`类 MixColumns 扩散` / `独立轮密钥` / `展开为独立轮` 这类命名，
   要么接上语义，要么在界面上标「近似 / 无效」—— 否则用户会拿教学近似当 AES 用。
2. **同一语义不许两处实现**。这套缺陷的根子是「掩码级传播」与「值级加密」各写了一遍，
   于是同一个 Δ 能同时得到三个答案。修法是**抽出一份实现**、另一处取它的线性延拓。
3. **只读的派生显示（分组长度）与引擎实际口径可以不一致**。凡是「界面显示的值由另一处派生」，
   就要把真正的口径（日志里的「词宽 32bit」）摆在同一个视野里。
4. **独立复核要能「测出平台自相矛盾」**：`verify-fangzhen.mjs` 的核心手法是
   **拿平台自己的加密校验平台自己的分析** —— 不依赖任何外部真值就能证伪，比对照 AES 更硬。
   缺陷修好后，同一批断言**翻转成正确性断言**（不是删掉）—— 这样它仍然是回归网。

守卫在哪儿：`verify-fangzhen.mjs`（11 节 **50 项**：GF(2⁸) 逐值对拍 + 掩码级/值级/真 AES 三方一致
+ 分支数 5 + 独立复现类 AES 222.00、能力边界与源码守卫）、`design-fangzhen.cjs`（真实浏览器留档）。

### 4.36 「两种分析算出来一样」的两个层次：一个是真相等，一个是我们没告诉他

用户问：「为什么差分分析和线性分析显示的数据一样？现在的算法不是我给双鱼 Feistel 吗？」
实测（2026-10-14，节点直跑 + 真浏览器）—— **两个独立的原因叠在一起**，别只修一个。

**① 双鱼这张图，差分与线性**本来就相等**（不是 bug）。**
把 `outputs/双鱼Feistel设计记录/shuangyu-project.json` 直接喂引擎，两条链路各算一遍：

| 模式 | 累计 −log₂p | 活跃 S 盒 | 逐轮输出掩码链 |
|---|---|---|---|
| 差分 | **66.00** | 11 | `1f00 → a30001 → 69000000 → a3009b → 7700 → 35009b → f5000000 → 35001e` |
| 线性 | **66.00** | 11 | `4800 → 1d0001 → 3b000000 → 1d0057 → 1200 → 1a0057 → 2d000000 → 1a0056` |

**总数相等是必然的**：AES S 盒 `DU = 4` → 单盒差分代价 `−log₂(4/256) = 6.00`；
`linearity() = 16`（= `max|LAT|`，`corr = 16/128 = 2⁻³`）→ 单盒线性代价 `−log₂(corr²) = 6.00`。
两个都是 6.00，而传播核每轮对每个活跃 S 盒都**取最优**（`bestTransition`），
字节活跃模式又只取决于「哪些字节非零」（一进一出）→ 两边逐轮活跃数也完全相同
（`1,1,2,1,2,1,2,1` = 11）→ 双双 **66.00**。
**但特征不是同一条**（上表两条掩码链不同）—— 别把「总数相等」读成「结果没换」。
（对照组：SM4 32 轮差分 **647.00** vs 线性 **642.00**，是**不同**的 —— SM4 的 DDT 里有
prob=2/256 的项，差分代价会取到 7.00。）

**② 更常见的那一半：跨页时页面显示的是「上一个模式」的结果，而且不吭声。**
`result` 在整站共享（sessionStorage 里只有一份），`AnalysisView` 换页**不会自动重算**。
实测：差分页跑完 → 点导航去「线性分析」→ 标题写着「每一步查 LAT」，
却原样显示 **647.00** 和差分那一整张逐轮表；点「运行分析」才变 **642.00**。
`ResultsView` 更糟：徽标与「中文解析」口径读的是**当前会话模式**（`mode.value`），
所以会给一份差分结果打上「线性」标签 —— **界面在替结果说谎**。

**修法（2026-10-14）：**

- `AnalysisView` 加 `staleMode` computed：`result.mode !== 当前页 mode` 时，在结果区上方弹
  `.stale-result` 警告，点明「显示的是**差分**的结果，点运行分析才用本页 LAT/DDT 重算」。
- `ResultsView` 的徽标 / 解析 hint / 导出报告 `mode` 一律改读
  `resultMode = result.char.mode || result.mode || mode` —— **跟着结果走，不跟着页面走**。
- **顺手拔掉一颗同类的雷**：`ResultsView.runCompare()`（三模型对比）自己抄了一份分流条件
  `feistel || mode === LINEAR` —— 正是 §4.33 在 store 里修掉的那个写法。于是**线性**模式下
  所有图（含 SPN）都被送进 SM4 味的 Feistel 迭代引擎，图被忽略，对比数字与「运行分析」对不上。
  修法：把 `runProfile` 从 store **export** 出去，结果页直接复用 —— **分流规则只有一份**；
  对比时显式传 `mode: resultMode.value`，**跟着结果口径走，不跟当前页**。
- **补一条界面说明**：分析页标题下常驻一句「两种模式的 −log₂p **可能相等**，这不是算错」，
  并给出 AES 盒的例子（差分 4/256 与相关度 16/128 权重都恰好 6.00）+ 判据
  （「比较输入/输出掩码即可分辨 —— 引擎走两套独立计算」）。否则用户看到 66.00 = 66.00
  仍会读成「两种分析一模一样」。
- 守卫：`verify-pages.mjs` +6 条（`runProfile` 必须 export／结果页不许再出现 `isFeistel`、
  `mode === MODE.LINEAR ||`、`feistelCharacteristicSearch(`／分析页必须有 `staleMode` +
  `.stale-result`／结果页口径必须取自 `resultMode`／分析页必须写明「可能相等」不是算错）；
  `e2e-browser.cjs`【12】+5 条真浏览器断言（差分 647 → 跳线性页出现警告 → 重算 642 → 警告消失）。

**通用教训**：**跨页共享的「物证」（result / 图 / 参数）必须记住自己是从哪个口径产生的**，
显示层要按物证**自己的**口径渲染。只按「当前页的状态」渲染共享物证，就会出现
「标题说 A、数字是 B」—— 这类错误**所有静态测试都会过**，只有真点一遍才看得见。
